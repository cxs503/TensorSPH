# TensorSPH 项目分析

**日期：** 2026-10-23
**范围：** 仓库当前 HEAD（`ba7d1ae`，version 0.4.0），全部结论来自在本机重新运行代码，而非阅读文档转述。
**环境：** Debian / Python 3.11.2 / torch 2.14.1+cu130（CPU，2 线程）/ numpy 2.4.6 / matplotlib 3.11.2 / 无 GPU。

---

## 1. 结论摘要

**这是一个少见地"诚实"的科学计算原型：** 代码量小（约 2.7k 行 Python + 1.3k 行文档）、模型清晰、边界条件与验证证据可复现。它的核心价值不在于 SPH 算法本身（都是文献中的标准做法），而在于**把"程序跑通了"和"物理正确"严格分开**的工程契约：三个独立状态位、逐条验收指标、失败的运行也落盘。

复现结果：**67 个测试全部通过（9.3 s）**；README 中所有可复现的数字我都跑出来了，包括 B1 静水压 `1.086 %`（文档 1.09 %）、B2 观测收敛阶 `0.960`（文档 0.96）、邻域搜索微基准、默认 750 步运行 5.4 s。

主要问题不在数值方法，而在三类：

1. **门禁的真实性漏洞**（最高优先级）：`mass_conserved` 是一条**恒真门禁**——它的测量值在代码里被硬编码为 `0.0`，永远不会失败；验收指标只在 `output_every` 采样点计算，步间超调会漏检；`validate_config` 只校验声学 Courant，缺少粘性 CFL，我实测 `viscosity=1.0` 时配置被接受但运行发散到密度压缩 53 %–160 倍。
2. **配置接口说谎**（中等）：`DamBreakConfig(device="auto")` 直接抛 `RuntimeError`；`run_case` 完全忽略 `cfg.boundary`（传 `"clamp"` 仍用壁面粒子，静默）。两个 benchmark 脚本各有一个声明了但永不生效的命令行开关。
3. **性能瓶颈是调度开销而不是浮点运算**：`rhs` 每次调用产生 **702 次 ATen 算子调用**（48 种算子），空转算子约 1.8 µs，仅派发就约 1.2 ms，占 608 粒子时 2.2 ms/步的 **~55 %**；另有 10 次 `index_add` 约占 25 %。GPU 在这个规模不会带来收益，`torch.compile` 才是关键杠杆。

对外的"科学主张"部分则是干净的：没有任何一处把未验证的物理说成已验证，实验对比门明确标为 `not_evaluated` 并解释了为什么缺数据。

## 2. 项目概况

| 项目 | 事实 |
|---|---|
| 定位 | PyTorch 原生的弱可压缩 SPH（WCSPH）研究求解器，面向 agent 驱动的科学计算 |
| 物理范围 | 2-D 液滴入水（droplet impact）+ 2-D 溃坝（dam break，B2） |

## 3. 架构

```
neighbor_search.py                 droplet_impact.py                    dam_break.py
├─ brute_force_pairs  (oracle)     ├─ Config            ← 全局配置      ├─ DamBreakConfig(Config)
├─ cell_linked_pairs (device)      ├─ 核函数 W, ∇W                     ├─ make_column()
├─ cell_linked_pairs_host (对照)   ├─ tait_pressure()                  ├─ run_case()
└─ PairListCache (Verlet skin)     ├─ make_particles() / wall_lattice()└─ (复用 rhs / wall / boundary)
                                   ├─ rhs() / rhs_all_pairs()
                                   ├─ apply_boundary()
                                   └─ run() → CSV / .pt / PNG / manifest
                                        ↑
                              __main__.py 与 examples/run.py（两份几乎相同的 CLI）
```

数据流（一个时间步）：`pos` → `PairListCache.get` → `rhs` → `rho, p, acc` → 诊断采样 → 半隐式 Euler → `apply_boundary`（原地 clamp）→ 下一步。

**结构上的主要问题**：`droplet_impact.py`（763 行）同时承担了"SPH 数值内核"和"液滴算例"两件事，而 `dam_break.py` 反向从它 import 内核。命名也透露出这个耦合——`from .droplet_impact import Config, rhs, wall_lattice`。建议拆成 `core.py`（kernel/EOS/rhs/boundary/wall）与 `cases/`，这样第三个算例不需要再"借"液滴模块。

## 4. 数值方法评估

| 组件 | 实现 | 评价 |
|---|---|---|
| 核函数 | 2-D 三次样条，σ=10/7πh²，q≥2 截断 | 正确；梯度在 r=0 处返回 0，无 NaN |
| 密度 | 求和式 `ρ_i = Σ m_j W_ij` | 标准做法，但自由面低估 42 %（默认算例初始 ρ_min=582） |
| 状态方程 | Tait，`p = B((ρ/ρ0)^γ − 1)`，**在 0 处截断** | 消除拉伸不稳定；作者明确说明这不是表面张力模型 |
| 压力力 | 对称形式 `−(p_i/ρ_i² + p_j/ρ_j²)∇W` | 正确，与稠密参考在 float64 下 `rtol=2e-10` 一致 |
| 粘性 | Morris 正则化 Laplacian，含系数 2（`VISCOUS_LAPLACIAN_FACTOR`） | 有标定测试（施加/理论 = 1.000±1e-3），这是加分项 |
| 壁面 | 3 层静态 dummy 粒子，Adami 压力外推 + Tait 反解壁密度 | 有效（B1 1.09 %），但**只实现了 Adami 式的核加权平均项**，省略了体力/加速度项（见 P1-4） |
| 时间推进 | 半隐式 Euler，固定 dt | 一阶，与 B2 观测阶 0.96 自洽 |
| 邻域搜索 | 均匀 linked-cell，cell=cutoff，`unique`+`searchsorted`+`repeat_interleave` 全设备端 | 与暴力枚举逐位一致（1/2/3-D、边界情形、400–5000 粒子） |
| 缓存 | Verlet skin，`skin=0.25h`，位移 > skin/2 重建 | 正确；实测 12.1 步/次重建 |

数值上我认为**没有发现真正的错误**：符号、对称性、核归一化、量纲都对得上，粘性项与压力项的动量反对称性也正确。争议点都在"模型完备性"而非"实现正确性"。

### 5.3 性能剖析（608 流体 + 291 壁面，7918 对）

| 部件 | 耗时 | 备注 |
|---|---|---|
| `rhs`（复用 pairs） | 2.21 ms | 0.28 µs/对 |
| `cell_linked_pairs`（每步重建） | 2.33 ms | 与力计算同量级 → 缓存是必需品 |
| `PairListCache.get`（仅位移检查） | 0.01–0.03 ms | 很便宜 |
| 单次 ATen 小算子 | 1.80 µs | 每次 `rhs` **702 次调用**、48 种算子（其中 `aten::to` 56 次、`aten::empty` 41 次） |
| `index_add` 1-D / 2-D(P,2) | 20 µs / 100 µs | `rhs` 共 10 次（含壁面外推 4 次），≈0.5 ms |
| `scatter_add` 1-D | 11 µs | 比 `index_add` 快 1.8x |
| `_plot` | 1.56 s | 400 步运行总计 3.0 s 中的 **52 %** |

**结论：这是 dispatch/launch 受限，不是算力受限。** 典型证据是 `rhs` 从 2529 对涨到 27846 对（11 倍）时耗时只从 1.23 ms 涨到 6.37 ms，固定开销约 0.8 ms；702 次算子调用 × 1.8 µs ≈ 1.26 ms，占实测 2.21 ms 的 57 %（其余是 `index_add` 的原子路径与大张量分配）。因此：

- **GPU 在小规模上不会更快**（700 次 launch × 每 launch 数 µs 的 GPU 端延迟通常更差），这解释了为什么仓库"CUDA 从未在 GPU 上基准测试"也不算致命；
- **`torch.compile` 是最有价值的单一优化**（融合 elementwise 链、减少 launch）。本沙箱缺 C++ 工具链无法实测其加速比，建议在 CI 之外的机器上验证；
- **`index_add` → `scatter_add` 或按分量拆开**是低风险、可测量的改进（本机 1-D 快 1.8x）；
- **绘图应默认关闭或异步**，否则小算例的墙钟被 matplotlib 主导。

### 5.4 分辨率敏感性（固定物理时间 t=0.30 s，dt=0.9×Courant）

| dx | 粒子 | 步数 | 墙钟 | max\|v\| | ρ_min | KE |
|---|---|---|---|---|---|---|
| 0.025 | 608 | 684 | 2.7 s | 0.701 | 806 | 13.52 J |
| 0.0125 | 2436 | 1368 | 10.8 s | 0.725 | 747 | 13.79 J |
| 0.00625 | 9760 | 2735 | 70.4 s | 0.748 | 691 | 14.36 J |

全局量（速度、动能）在 3–4 % 内收敛，但**自由面密度亏损随分辨率单调加深**（−19 % → −25 % → −31 %）。这与"没有 delta-SPH / 密度扩散"一致，也再次说明液滴算例目前只能当 smoke case，不能当科学基准——文档也是这么写的。

### 5.5 精度与稳定性

- float32 vs float64 跑 750 步：max\|v\| 相对差 **2.1e-6**，最大位置差 **1.9e-5 m（0.001 dx）**。float32 在本例足够，但 `Config` 没有 dtype 入口。
- **粘性 CFL 未校验**：`ν=1.0`、`dt=4e-4`（粘性极限应为 `0.125h²/ν≈3.3e-5`，超标 12 倍）时 `validate_config` 放行，运行后密度压缩 53 %、Mach 1.18；`ν=2.0` 时压缩 160 倍。fail-fast 事后抓到了（门禁有效），但应该启动即拒绝。
- `dx` 细化时 `dt` 不会自动跟随，用户必须自己调（`suggested_dt` 存在但 `run` 不会提示），细化后直接抛 `ValueError` 是合理但生硬的体验。

## 6. 问题清单

### P0 — 门禁/契约的真实性

**P0-1 `mass_conserved` 是恒真门禁。**
`benchmarks/dam_break/run.py:135` 把 `"mass_drift_kg"` 硬编码为 `0.0`，第 266–268 行的判定就是 `0.0 == 0.0`。也就是说这条 gate 在任何输入下都不可能失败，它验证的是"常量没有被重新赋值"，而不是"模拟没有丢质量"。
*建议：* 由 `run_case` 在起点/终点分别返回 `mass.sum()`（它已经存在 `run.mass` 字段），门禁比较两次求和；否则把该 gate 删掉，避免"看起来有 7 条门禁"的错觉。

**P0-2 验收指标只在输出步采样。**
`droplet_impact.py:671` 的 `if step % cfg.output_every == 0` 决定了 `rho_max / max_speed / courant` 只在采样点进入 `rows`，而 `evaluate_acceptance` 只读 `rows`。默认 `output_every=50`，意味着第 1–49 步的峰值密度、峰值 Mach、Courant 超限完全不可见。
*建议：* 在积分循环内累加 4 个标量极值（每步 4 次 `torch.max`，成本可忽略），门禁读累加器而不是采样表。

**P0-3 `validate_config` 缺少粘性（和体积力）CFL。**
`droplet_impact.py:475` 只校验 `dt·c0/h ≤ max_courant`。实测 `viscosity=1.0` 被接受后发散（见 5.5）。文档把"时间步已验证"当成已验证项，但只覆盖了声学限制。
*建议：* 增加 `dt ≤ 0.125 h²/ν`（Morris/ESPHS 常见判据）与 `dt ≤ 0.25√(h/g)`，失败时像现在一样报出允许的最大步长。

### P1 — 接口与模型一致性

**P1-1 `run_case` 静默忽略 `cfg.boundary`。**
`dam_break.py` 全文不引用 `cfg.boundary`，`run_case` 无条件构造壁面粒子。实测 `DamBreakConfig(boundary="clamp")` 正常返回且 `escaped=0`——用户以为切换了边界模型，实际上什么都没变。这比报错更危险。
*建议：* 要么实现该分支，要么在 `validate_case` 里 `if cfg.boundary != "wall": raise ValueError(...)`。

**P1-2 `DamBreakConfig(device="auto")` 抛 `RuntimeError`。**
`dam_break.py:138` 用 `torch.device(cfg.device)`，绕过了 `resolve_device`（`droplet_impact.py:759`）。而 `DamBreakConfig.device` 的默认值是 `"cpu"`，所以问题只在用户显式传 `"auto"` 时暴露，报错信息是 torch 的 device 解析错误，难以定位。
*建议：* 统一走 `resolve_device`。

**P1-3 两个命令行开关是死代码。**
- `benchmarks/neighbor_search/compare.py:44`：`--include-host` 是 `store_true` 且 `default=True`，**永远为真**，无法关闭 host 对照。
- `benchmarks/dam_break/run.py:197`：`--observed-order` 声明后从未被读取；第 257 行的条件只看 `len(results) >= 3`，所以传不传这个开关结果一样。

**P1-4 壁面压力外推与"Adami et al. (2012)"的引文不完全对应。**
`droplet_impact.py:334–347` 实现的是 `p_w = Σ p_f W / Σ W`，即 Adami 式 (11) 的**核加权平均项**；参考式还包含体力/加速度项 `ρ_f (g − a_w)·(r_w − r_f)`。省略它对静水压影响很小（B1 通过），但会让"已实现 Adami 边界"这一表述强于代码。
*建议：* 在 docstring 与 README 中改为"Adami 的核加权简化形式"，或补上重力项并重跑 B1。

**P1-5 2-D 核归一化是硬编码的，但接口不限制维度。**
`cubic_spline_kernel` 的 σ=10/(7πh²) 只对 2-D 成立，而 `neighbor_search` 明确支持 1/2/3-D。`rhs`/`run` 没有断言 `pos.shape[1] == 2`，三维调用会静默得到错误的密度与力。
*建议：* `rhs` 入口断言 2-D，或把 σ 与维度绑定。

**P1-6 快照全部驻留内存。**
`droplet_impact.py:694` 把每个输出步的 `pos`、`rho` 克隆进 `snapshots` 列表，直到运行结束才写盘。`output_every=1` 的长跑是 O(steps·N) 内存。
*建议：* 边算边写，绘图时只保留抽样索引（`_plot` 反正只画 12 帧）。

### P2 — 性能

**P2-1 绘图占比过高。** `_plot`（`droplet_impact.py:729`）在 400 步运行中占 52 % 的墙钟（matplotlib import 约 0.6 s + savefig 0.7 s），默认 750 步运行约 28 %。建议加 `run(..., plot=False)` / CLI `--no-plot`，让绘图不再进入关键路径。
**P2-2 `index_add` 是大头。** 每次 `rhs` 有 10 次（密度 2、壁面外推 4、压力 2、粘性 2），2-D 情形单次 100 µs。`scatter_add` 本机 1-D 快 1.8x；也可把 (P,2) 累加拆成两个 1-D。
**P2-3 每步重新 `torch.cat((pos, wall))`。** `run` 第 663 行与 `rhs` 内各拼一次；可以预分配 `all_pos` 缓冲区并原地写入 `[:n]`，省掉每步两次分配。
**P2-4 CUDA 路径未验证且每步同步。** `PairListCache.displacement` 用 `float(...)`、诊断用 `float(...)`，每步至少一次 host 同步；`index_add` 在 CUDA 上走原子路径，结果非按位确定。既然从未在 GPU 上跑过，建议要么在 CI 里加一个 `device=cuda` 的可跳过用例，要么在 README 里把"Cuda 可用但未验证"写得更醒目。

### 测试覆盖缺口

## 7. 建议路线

**第一周（正确性，全部是小改动）**

1. 修 `mass_conserved`：用真实质量求和（P0-1）。
2. 门禁改为每步累积极值（P0-2），并在 manifest 里记录 `sampled_steps` 与 `all_steps` 两种口径。
3. `validate_config` 增加粘性/重力 CFL（P0-3），配套单测。
4. `run_case` 统一 `resolve_device`、显式拒绝或实现 `boundary`（P1-1/P1-2）。
5. 删掉或实现 `--include-host`、`--observed-order`（P1-3）。

**第一个月（结构性）**

6. 把内核拆出 `tensorsph/core.py`，算例放 `cases/`；`dam_break` 不再从 `droplet_impact` import 内核。
7. `rhs` 增加维度断言与 `dtype` 入口（P1-5）。
8. 快照流式写盘 + `--no-plot`（P1-6/P2-1）。
9. 补 LICENSE、optional extra、ruff/mypy 与覆盖率（P3-1..P3-4）。
10. 用 `scatter_add` 或按分量累加替换 2-D `index_add`，在 benchmark 里记录前后对比（P2-2）。

**季度（科学性）**

11. **唯一的科学阻塞项仍是实验数据**：B2 缺 Martin & Moyce 的数字化表。项目已说明数据不可自由再分发，因此更现实的做法是：(a) 允许用户提供 CSV 路径与 provenance 字段，把 `experimental_reference` 从 `not_evaluated` 变成"可用但未提供"；(b) 或改用有开放数据集的基准（如 Aureli et al. 2023 综述中若有附表）。
12. 自由面处理从"压力截断"升级到 delta-SPH 或 Monaghan 人工应力，并**与截断方案做并排对比**（这才是 P1 列表里真正未解决的一项）。
13. 自适应时间步：`dt` 在运行中随 `max|v|` 调整，并把"当前限制判据"写进 manifest。
14. 若确有必要上 CUDA，先在真实 GPU 上跑 `benchmarks/neighbor_search/compare.py --device cuda` 与一个 10k 粒子算例，确认相对 CPU 的收益，再决定是否优化。

**新发现（修改过程中测出）**：溃坝算例的密度压缩峰值并不来自整体流动，而是

t = 0.661 s 触壁；触壁前的"体相"最大值只有 1.8–2.4 %。改用逐步极值后，
`density_compression` 门禁在 10 % 限值下**不再通过**（9.7 / 10.3 / 10.0 %），

`bulk_compression` 单独报告体相值。

5.02–5.18 s → 4.50–4.70 s（加 `--no-plot` 3.51–3.59 s）；溃坝 `dx = 0.01`
32.3 → 22.6 s。400 步轨迹与旧实现**逐位相同**。

## 8. 总体评价

| 维度 | 评价 |
|---|---|
| 数值正确性（实现层面） | **高**：算子与稠密参考逐位/1e-10 级一致，粘性有解析标定，邻域搜索有暴力枚举 oracle |
| 数值完备性（模型层面） | 中：无表面张力、无密度扩散、壁面外推是简化版、2-D 专用 |
| 科学诚信 | **很高**：三状态位、失败也落盘、实验门明确 not_evaluated 并解释原因 |
| 可复现性 | **很高**：文档里 7 组数字我全部复现，误差在打印精度内 |
| 性能 | 中：算法选型合理，但受 Python/torch 派发限制；缓存策略是正确决策 |
| 工程质量 | 中上：测试质量优于数量，但缺 LICENSE、lint、覆盖率；文档有版本漂移 |
| 可扩展性 | 中下：内核与算例耦合在一个 763 行文件里，第三个算例会放大这个成本 |

一句话：**作为"可审计的 SPH 原型"，它已经越过了大多数同类项目停下的地方（自证数字、区分执行与验证）；作为"可扩展的求解器"，它下一步该做的是拆内核、补门禁漏洞、以及解决那个唯一的真问题——参考数据。**
