# CASE-SPH-WEDGE-ENTRY-2D — 细网格 shard abort 的归因审计（rc=134）

**锚点**: `CASE-SPH-WEDGE-ENTRY-2D`（算例池·二维楔形体入水砰击压力，`feature_ledger` 状态 `open`）
**本单**: m22495（tp-infra-2 自找活）　**日期**: 2026-11-15
**工件**: `benchmarks/case_sph_wedge_entry_2d/heap_probe.py`、`thread_scan.py`、
`tests/test_wedge_thread_scan_harness.py`（10 项）、集群 `cj4173` / `cj4177`
**本轮无新判据、无新参考值**：改的是「上一轮为什么读不到细网格」这个**归因**，不是读数本身。

## ① 案例与问题（为什么要审这个）

该算例的判决需要**锯齿梯子**上 ≥2 个可判网格（`dx = 4/2/1/0.5 mm`）。已提交读数只有 `dx=4/2 mm`；
`dx=1 mm` 只从旧档位数里读到一次（`literature_regrade`：6.805，U=6.5 %，PASS），
`dx=0.5 mm` **从未取回**。三次 abort 的原始记录（`/srv/tensor/agent/cluster/jobs/*.log`）：

| jid | 命令 | 观测 |
|---|---|---|
| cj3803 | `--shard 3`（dx=0.5 mm）`--threads 16` | rc=134 `free(): corrupted unsorted chunks` |
| cj4103 | `--shard 2`（dx=1 mm）`--threads 8` | rc=134 同上 |
| cj4106 | `--shard 1`（dx=2 mm）`--threads 8 --dump-frames` | rc=134 同上 |

上一轮（m22416 报告 ⑤-2、cj3803 条目）把这三次 abort 读成
**「分辨率相关的内存缺陷 / 最细网格脆弱」**，并把 `dx=0.5 mm` 的缺失归因于算力与内存。
这是个**未检验的归因**：三次 abort 全部发生在 `--threads ≥ 8`，而本算例**所有已提交工件**都是
`--threads 4`（`ensemble_peak` 的默认值）。分辨率轴与线程轴在这批证据里是**共线**的，
不能据此说「细网格坏」。

## ② 怎么做的（方法/流程/工具链）

1. **把共线拆开**。新增 `thread_scan.py`：一个 shard = 一个 `(dx, threads)` 单元，
   跑**同一个**估计量（`ensemble_peak` 的阶梯读数 + footprint bootstrap），
   干净退出才写工件，并把 <0.5 kB 的摘要打到 stdout（集群日志 8 kB 尾截断）。
   两张单元表：`CELLS`（2/1 mm × 4/8/16 线程）与 `CELLS_FINE`（1/0.5 mm × 8/16/32 线程），
   覆盖「已提交的 4 线程」与「abort 的 8/16 线程」两端。
2. **本地复现（先做，最便宜）**：本机 loongarch64 / torch 2.7.1 / CPython 3.11.6，
   用 `MALLOC_CHECK_=3 MALLOC_PERTURB_=165` + `-X faulthandler` 跑真实阶梯 shard，
   让潜在溢出当场 abort 而不是延后。
3. **排除运行时假设**。新增 `heap_probe.py`：`/proc/self/maps` 统计映射进来的 OpenMP 运行时份数
   （重复 libgomp/libomp 是这句 abort 的教科书成因），并用**纯 torch** 最小负载
   （随机矩阵乘 ×8，无任何 SPH/楔形体代码）在 1/2/4/8/16 线程下对照；
   每个场景独立子进程，返回码就是数据。
4. **观测通道本身取证**：比对作业终态与作业日志的 `rc`。

## ③ 计算结果（程序化注入）

### (a) 本地真实阶梯 shard（MALLOC_CHECK_=3，全窗 61 帧）

| dx | threads | rc | 分辨率带 peak_median | band spread | jackknife_rel | wall |
|---|---|---|---|---|---|---|
| 4 mm | 8 | 0 | **10.04148** | 23.53 % | 0.0012 | 13.0 s |
| 4 mm | 16 | 0 | **10.04148** | 23.53 % | 0.0012 | 19.5 s |
| 2 mm | 7 | 0 | **6.07082** | 11.83 % | **0.4295** | 73.8 s |
| 2 mm | 8 | 0 | **6.07082** | 11.83 % | 0.4295 | 68.9 s |

（"顶层级" `peak_median` 分别 12.139 / 7.063，与已提交工件同名量一致；上表取判据所用的**分辨率带**量。）

`dx=4 mm` 在 8 与 16 线程下给出**逐位相同**的 5 档读数序列（15.809 / 15.368 / 12.139 / 12.139 / 12.139）
→ 估计量对线程数**不变**，不存在「线程相关的数值抖动」这条隐藏不确定度源。

### (b) 与已提交工件的一致性（这是本单最强的一条）

已提交 `dx=2 mm`（4 线程）读数 `6.071`、不确定度 `43.0 %`；本单 **8 线程**重跑得到 `6.07082`、`42.95 %`。
已提交 `dx=4 mm`（4 线程）读数 `10.041`、不确定度 `23.5 %`；本单 **8 线程与 16 线程**均得到 `10.04148`、`23.53 %`。
→ 合并后的树在**会 abort 的那个线程数**下，给出与已提交工件**一致**的读数，且**不 abort**。

### (c) 运行时假设的检验

| 场景 | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| 纯 torch 最小负载 rc | 0 | 0 | 0 | 0 | 0 |
| `import torch` + set_num_threads rc | 0 | 0 | 0 | 0 | 0 |
| 映射的 OpenMP 运行时 | 仅 `/usr/lib64/libgomp.so.1.0.0`（**1 份**） | | | | |

→ 「重复 OpenMP 运行时」假设在**本机**被否定；候选缓解（`OMP_NUM_THREADS=1` / `OMP_WAIT_POLICY=PASSIVE` /
关掉 malloc 检查）全部 rc=0，即本机根本没有可复现的失效，无法用来挑缓解。

### (d) 通道取证（**这是另一个真实缺陷**）

| jid | 作业日志 rc | 调度系统终态 |
|---|---|---|
| cj4103 | **134**（`free(): corrupted unsorted chunks`） | `succeeded`（rc 0） |
| cj4106 | **134**（同上） | `succeeded`（rc 0） |

→ 崩溃的 shard 在队列里被记成**成功**。这直接解释了上一轮为什么以为「细网格还在排队」：
**没有工件、但状态是成功**的作业，看起来与「还没跑到」无法区分。

## ⑤ 注意点（不粉饰）

1. **本机不复现 ≠ 节点不复现**。本单在本地覆盖了 `dx=4/2 mm × 8/16 线程`（干净），
   但 `dx=1 mm`（cj4103 崩的那个）与 `dx=0.5 mm`（cj3803 崩的那个）在本机跑不起（超出 <8 核 / <10 min 纪律），
   已递交集群 **cj4173**（2/1 mm × 4/8/16）与 **cj4177**（1/0.5 mm × 8/16/32，`heap_probe` 同步随作业分片跑）
   作为判别实验。**写作时两单仍在排队**，因此「abort 与 (网格, 线程) 无关」目前只在 4/2 mm 上成立，
   `dx ≤ 1 mm` 仍是 `WITHHELD`——不预判。
2. **暂存树假设已排除**：`diff -rq` 显示 `m22416`（递交 cj4103/cj4106 的那棵树）与本树 `benchmarks/case_sph_wedge_entry_2d/*.py`
   **逐字相同**（仅 `artifact_digest.py` 与 `__pycache__` 不同），所以「草稿代码有 bug」不成立。
3. **`rc=0` 的判据本身不可靠**：本单给 `thread_scan.py` 的摘要行加 `DIGEST` 前缀，就是为了让
   「没有摘要行」成为可检的失败信号（下一轮据此判断，而不是看终态）。
4. **不改变任何读数**：`dx=2 mm` 仍对 Z&F 复合解 6.92 差 −12.3 %、不确定度 43 %（不可判）；
   本单不改善精度，只把「为什么读不到」这件事从不成立的说法（分辨率脆弱）改成可判别的问题。
5. **尚未定位根因**：如果 cj4173/cj4177 在节点上复现 rc=134，那么判别已缩小到「节点环境（allocator/镜像）
   vs 本机」；`heap_probe` 在作业内打印的 OpenMP 映射表会是第一个可查证据。

## ⑥ 误差判定（逐项，显式回答是否 < 3 %）

| 量 | 基准 | 结果 | 偏差 | < 3 % ? |
|---|---|---|---|---|
| `dx=2 mm` 分辨率带读数（8 线程，本单） | 已提交 4 线程工件 6.071 | 6.07082 | −0.003 % | **是** |
| `dx=2 mm` 不确定度（8 线程） | 已提交 43.0 % | 42.95 % | −0.1 % | **是** |
| `dx=4 mm` 分辨率带读数（8 / 16 线程，本单） | 已提交 10.041 | 10.04148 | +0.005 % | **是** |
| `dx=4 mm` 5 档读数（16 线程 vs 8 线程） | 同序 | 逐位相同 | 0 % | **是** |
| `dx=1 mm` / `dx=0.5 mm` 是否 abort | cj4103 / cj3803 的 rc=134 | **未取回（排队中）** | — | **无基准，不可判** |
| abort 根因 | — | 未定位 | — | 无基准，声明为 `WITHHELD` |

**回答「是否 <3 %」**：机制层面**是**——线程数不改变读数（0 %），合并树在 8 线程上复现已提交工件（<0.01 %），
因此「崩溃是数值/分辨率现象」这个说法没有支撑；但**根因层面不是**——本单没有定位 abort 的根因，
`dx ≤ 1 mm` 的判别实验仍在队列里，照实记为 `WITHHELD`，不以「本机不复现」冒充结案。

## ⑧ 给下一次自找活的线索（按价值排序）

1. **取回 cj4173 / cj4177 的 `DIGEST` 行**（一次 `fetch`/`status` 即可）：
   * 若干净 → 「分辨率脆弱」彻底否定，用它们的读数**补齐 1 mm / 0.5 mm 两档**，判决可能由此闭合（4 档齐全）；
   * 若 rc=134 → 拿作业内的 `heap_probe` OpenMP 映射表 + `nproc` 对照本机，转查节点镜像差异。

   否则「无工件的成功作业」会持续被误读为「还在排队」。

   这是唯一可能让读数真正靠近参考的方向，属重计算。
